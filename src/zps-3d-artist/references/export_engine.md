## D. Check → export → report
**Receive:** the model and the target standard: format, units/axes/pivot, data to keep, budget, and reviewer.
1. Compare art and technical aspects separately. Render clay/wire/checker/ID to answer the question at hand. A beauty render only helps with the overall view. For a quantitative image comparison, fix the projection/camera/framing, the resolution, the align/mask, and the color space. Verify an ID or color pass by readback. Do not infer correct pixels from the render settings.
2. Use IoU, landmark, and DeltaE only when a valid measurement standard exists. Record the definition, the unit, the source of the threshold, and the limits. Do not use a pilot threshold as a general certification. Do not use it to hide identifying detail. If a metric is not done, write `not checked`. Do not invent a number or a pass. The reviewer can still comment on the image, with a clear scope.
3. Export a separate build for the task. Keep the editable source. Check the data after export: dimensions/bounds/pivot/axes, triangles/vertices/material slots, UV/normals, and attached resources. Do not use the same FBX/GLB preset for every engine. Check the front with meaningful landmarks/markers and world transforms. Do not check only the local axis names.
4. When it fits, import again in a clean scene and compare the important properties. If you did not do this, or could not, write that. Read the section "Integrate and check a model in the engine" below when the task requires engine integration. An import without errors does not prove correct gameplay, rendering, or performance. Do not copy the asset into a project outside the scope on your own.
5. Call an independent reviewer only when the task assigns one and the reviewer is available. Send the brief, the style, and the locked points together with the source and the evidence. The review does not replace the visual approver or the technical approver. Keep the editable source. Keep the review milestone and the version that you need to reproduce. Do not require every edit to save the source, export, images, and report again. Run revision rounds under principle 6 in SKILL.md. If authority or budget runs out, or there is no progress, report the remaining faults with a recommendation.
**Handoff:** real files, and the results in the handoff report: version/run, changes, necessary figures, evidence, parts not checked, the real verdict, and the next step. `3D-BUILD-REPORT` is an optional structure. Output a separate file only when the task needs it. A script that did not run does not replace the model. If a target check is missing, write the milestone that you really reached. Do not call the asset game-ready.

**Recipient compatibility:** before handoff, identify the recipient viewer or application and the material data it supports. If you use vertex color, procedural materials, or an extension, check in the recipient that really uses them. A Blender roundtrip does not prove that another viewer shows the asset correctly. If support is not verified, recommend a portable version. The portable version uses an embedded base-color texture and a standard material. Keep the origin. Convert only within the task authority. Bake each part to its own target material or image if the UVs differ. Check that no shared material is overwritten. If you change the UVs for the portable version, record a separate version. Check that the geometry does not change. If you cannot open the recipient yet, write target-viewer pending. Do not claim that compatibility is reached.

**Owner of the export check:** the 3D Artist does the package/target check within the scope. Other people reuse the result for the same artifact, version, and conditions. The texture/material side helps diagnose the surface. Do not import or render again for the same check if nothing changed and no evidence is missing. Re-check only the changed part and what depends on it.
# Integrate and check a model in the engine

Read this when the task assigns an import, a runtime verification, or an asset optimization. Receive the engine/version/renderer, the platform, the camera, the interaction requirements, the budget, and the allowed write area. If there is no engine yet, conclude only the preflight. Do not silently choose a new engine as the standard.

1. Import the artifact of the correct version into the assigned test area. Keep the source. Record settings that you can repeat. Check the attached files, scale/bounds/pivot/axes, UV/normals/tangent, and material/maps/shader. Do not change the render pipeline or the project-wide configuration outside your authority.
2. View with a representative camera and light. Check the silhouette, the look, the proportions, and the placement. Check collision, LOD, animation, and deformation only if the task requires them. A headless import without errors only passes the import gate. It does not replace evidence of look or behavior.
3. If the task assigns a performance measurement, record the device, build, scene, resolution, settings, and instance count. Measure the CPU, GPU, memory, and draw calls that you can really get. State the limits of the tool. Triangle and material counts are only data or estimates. Do not infer FPS from them. If you have no device, write "not measured".
4. Optimize the asset within the assigned scope, based on the bottleneck and the budget. Compare before and after under the same conditions. Keep the look. If you must reduce quality beyond your authority, submit it to the visual approver or the task giver with a recommendation and the tradeoff. A custom shader, a whole-scene optimization, an automated pipeline, or a multi-device confirmation is a specialized task. Do not expand into it on your own.
5. The 3D Artist fixes mesh and UV problems. Hand texture and map problems to the texture/material side (or fix them yourself if assigned). Retest the changed part and the related parts. Record the effect on bake, texture, and rig. Do not only clear warnings when the construction is intentional.

Handoff: the requested scene or package, the artifact version, the import configuration, engine images, separate results for data/import, look/behavior, and performance, faults, and a recommended next step. If you build and then check the asset yourself, record it as a **self-check**. Use "independent review" only when another person or context does it. The visual approver still approves the art. A self-check does not replace that approval or the independent criteria of the task.

**Data present ≠ material uses it:** check both the exported attributes (for example, vertex COLOR_0) and the runtime shader or material that really consumes them. For a native Godot material that needs vertex color, check vertex_color_use_as_albedo on the exact surface that has the data. Do not enable it blindly on every surface. Capture the target result after a configuration change within your authority. Record before/after and retest. Keep the camera, light, exposure, and view transform comparable before you conclude that a color shift comes from the texture. Do not recolor the asset to compensate for a wrong configuration. Keep the data/import pass, the look pass, and the performance pass separate. An import with exit code 0 does not prove the other two.
